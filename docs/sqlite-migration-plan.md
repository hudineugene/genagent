# План перехода с SQLite

## Где мы сейчас (24 октября 2026)

- **База.** Один файл SQLite, встроенный в Node.js (`node:sqlite`). Режим WAL, `synchronous=FULL`, проверка внешних ключей. Доступ через drizzle (`sqlite-proxy`), один процесс — контейнер `genagent-bot`.
- **Объём боевой базы:** 6,1 МБ. Это 137 сообщений, 7 разговоров, 113 фрагментов базы знаний и 6 730 записей расходов. Запас огромный: SQLite спокойно держит десятки гигабайт и тысячи записей в секунду при одном писателе.
- **Резервные копии.** Ежедневная копия файла и файлов медиа, 7 последних хранятся на сервере, зашифрованная копия уходит в Telegram. Есть скрипт восстановления.
- **Особенности SQLite в коде** собраны в `src/db/dialect.ts`:
  - `jsonText(col, "a.b")` — чтение JSON-полей (context, meta, config), 21 место;
  - `messageSeq` — порядок вставки сообщений (`rowid`) для строк с одинаковым временем, 9 мест;
  - вне этого файла остаются только полнотекстовый поиск базы знаний FTS5 (`kb_chunks_fts`) и векторы в BLOB (`kb_chunks.embedding`), сходство считается в коде.

**Вывод: переходить сейчас не нужно.** SQLite — самый надёжный и дешёвый вариант для одного сервера. Переход нужен по признакам ниже, а не «на вырост».

## Когда переходить: признаки

Переходим, если выполняется хотя бы одно:

1. Нужно **два и больше экземпляров приложения** — для отказоустойчивости или из-за нагрузки. Писать в один файл SQLite они не могут.
2. В логах больше **1% ответов `SQLITE_BUSY`**, или p95 записи сообщения превышает 50 мс при `busy_timeout`. Сейчас это не так.
3. База больше **20 ГБ**, или ночная копия файла идёт дольше 10 минут.
4. Клиент требует **хранить данные в другой стране** (отдельная база на клиента) или подписать SLA с RPO < 1 часа (потеря данных не больше часа).

Пока признаков нет, раз в месяц смотрим «Биллинг» и `/api/health`. В ответе `/api/health` есть блок `db`:
- `sizeMb` — размер базы вместе с журналом WAL;
- `busyDay` — сколько раз за сутки база была занята (`SQLITE_BUSY`);
- `writeP95Ms` — p95 времени записи по последним 500 записям (`writes` — сколько их учтено).

Счётчики живут в памяти процесса и обнуляются при перезапуске.

## Шаг 0. Уже сейчас, дёшево и без риска

- **Потоковая копия базы (Litestream)** в S3-совместимое хранилище, например Cloudflare R2 или Backblaze B2. Даёт RPO около 1 секунды и восстановление за минуты, без изменения кода.
  Это закрывает пункт 4 (RPO) без смены базы. Делается одним контейнером рядом с `genagent-bot`.
- **Счётчики** в `/api/health` (сделано): размер базы, число `SQLITE_BUSY` за сутки, p95 времени записи. Они покажут момент, когда пора переходить.
- **Никаких новых зависимостей от особенностей SQLite** в новом коде:
  - JSON-поля читать только через `jsonText()`;
  - порядок сообщений — `createdAt`, затем `messageSeq`. Сортировать по `id` нельзя: id случайные (UUID) и порядок вставки не сохраняют.

## Куда переходить

| Вариант | Когда подходит | Плюсы | Минусы |
|---|---|---|---|
| **libSQL / Turso** (совместимый с SQLite) | нужны реплики для чтения и копии, а писатель по-прежнему один | почти без изменений кода: тот же SQL, FTS5, `json_extract`; встроенные реплики | писатель один; сторонний сервис или свой sqld |
| **PostgreSQL 16+** (с pgvector) | несколько экземпляров приложения, большая нагрузка, требования к SLA | несколько писателей, зрелые инструменты, pgvector для поиска по смыслу, JSONB | заметная переделка запросов; отдельный сервер или управляемая база |

**Рекомендация:**
- при признаке 4 (страна, RPO) — Litestream, а при необходимости отдельные файлы SQLite по клиентам;
- при признаках 1–3 — сразу PostgreSQL, минуя libSQL: промежуточный переход стоил бы почти столько же.

## Переход на PostgreSQL по шагам

1. **Схема.**
   - Описать схему drizzle для `pg-core` рядом с текущей: `src/db/schema.pg.ts`.
   - Типы: `integer timestamp_ms` → `timestamptz`, `text json` → `jsonb`, `integer boolean` → `boolean`, `blob` эмбеддингов → `vector(1536)` (pgvector).
   - Миграции — отдельной папкой `drizzle-pg/`.
2. **Запросы.**
   - `jsonText(col, "a.b")` переключить на `col->'a'->>'b'`; вызовы по коду уже идут через него.
   - Сообщениям добавить столбец `seq bigserial` (при переносе заполнить из `rowid`), а `messageSeq` переключить на `messages.seq`.
   - `onConflictDoUpdate` и `returning` drizzle поддерживает в обоих диалектах.
3. **Поиск по базе знаний.**
   - FTS5 заменить на `tsvector` с конфигурацией `simple` (русский и украинский смешаны) плюс индекс GIN.
   - Векторы перенести в `vector` с индексом HNSW, сходство считать в базе (`<=>`), а не в коде.
4. **Подключение.**
   - `src/db/client.ts`: по `DATABASE_URL=postgres://…` — драйвер `postgres` (`drizzle-orm/postgres-js`), иначе SQLite.
   - Два диалекта держать один релиз, затем удалить SQLite-ветку.
5. **Тесты.**
   - Все `scripts/test-*.ts` прогнать на копии базы, перенесённой в PostgreSQL. Сейчас они работают на копии SQLite (`caltest`).
   - Добавить сверку числа строк и контрольных сумм по ключевым таблицам: разговоры, сообщения, оплаты, расходы.
6. **Перенос данных.**
   - Скрипт `scripts/migrate-to-pg.ts` читает SQLite таблица за таблицей в порядке зависимостей (clients → agents → channels → conversations → messages → …) и пишет пачками по 1000 строк в транзакциях.
   - JSON переносить как есть, время — из миллисекунд, эмбеддинги — из BLOB в массив.
7. **Переключение (окно 10–15 минут ночью):**
   1. объявить окно и выключить опрос Telegram и почты (флаг);
   2. сделать последнюю копию SQLite;
   3. перенести данные;
   4. сверить данные;
   5. перезапустить с `DATABASE_URL`;
   6. проверить `/api/health`, тестовое сообщение в каждом канале и вебхуки Meta (их повторы Meta дошлёт сама).
8. **Откат.**
   - Файл SQLite не трогаем 14 дней.
   - Откат — перезапуск без `DATABASE_URL`. Сообщения, пришедшие после переключения, переносятся обратно скриптом по `createdAt`.

**Оценка работы:** 4–6 рабочих дней на шаги 1–5 и ночь на переключение.
